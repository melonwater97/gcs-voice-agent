# 当前接口设计

版本：1.0.0；核验日期：2026-10-16。所有自定义业务接口统一使用 `header + payload`，msg_id 统一为 `MSG-<UUID>`。服务端录音的完整 HTTP 契约见 [地面站对接接口](地面站对接接口.md)；语音/文字输入、任务状态与工具契约见本文档。

## 1. 参与方与调用方向

| 参与方 | 地址 / 实现 | 消息端点 |
|---|---|---|
| React 地面站 | web/，127.0.0.1:5173 | FRONT / GS-01 |
| Agent 服务 | agent/，127.0.0.1:18002 | BACKGROUND / AGENT-01 |
| MCP 工具服务 | integrations/mcp_server.py，stdio 子进程 | BACKGROUND / MCP-01 |
| 本地任务模拟 | simulator/backend.py，MCP 进程内 TaskStore | 进程内方法，不是额外服务 |

```text
React 地面站 ── HTTP JSON 信封 ──→ Agent
React 地面站 ←─ HTTP JSON 信封 ─── Agent
                                    │ ↑
                          MCP stdio 中的业务 JSON 信封
                                    ↓ │
                               MCP 工具服务
                                    │
                          本地 TaskStore 创建/保存/模拟执行
```

React 就是地面站，没有独立的地面站业务后端。Vite 托管前端资源，将 /api/* 和 /health 直接代理到 Agent。MCP 不向浏览器发送 HTTP 请求，任务结果随 Agent 本次语音或文本响应返回界面。无需 18001 端口、/tasks 接口或地面站回调。

## 2. 公共信封与协议边界

信封模型 `shared/contracts.py: Message[PayloadT]`，header 模型 MessageHeader，消息由 shared/messages.py 生成。两层固定为 header 和 payload，均为必填；不允许其他顶层字段。

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000007",
    "msg_type": "HEALTH_QUERY",
    "version": "1.0.0",
    "src": {
      "type": "FRONT",
      "id": "GS-01"
    },
    "dst": {
      "type": "BACKGROUND",
      "id": "AGENT-01"
    }
  },
  "payload": {}
}
```

| header 字段 | 规则 |
|---|---|
| msg_id | MSG- 加标准小写 UUID，含连字符；生成器使用 UUID v4 |
| msg_type | 当前动作的消息类型，见下表和各阶段 |
| version | 固定 1.0.0 |
| src / dst | {type, id}；type 为 FRONT 或 BACKGROUND，id 为 1–64 字符 |

msg_id 正则为 `^MSG-[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`。Python 使用 uuid4，React 使用 crypto.randomUUID；没有日期流水号或跨标签页计数器。task_id 仍在创建时生成，继续使用 TASK- 加 32 位 hex。

所有 HTTP 和 MCP 工具业务请求、成功结果及业务错误采用信封。Agent 对地面站的所有 HTTP 响应统一使用 `msg_type: "AGENT_OUTPUT"`，成功响应种类由 `payload.type` 区分；任务结果只有 `task_result` 和 `clarify` 两种，错误响应不带 `type`，以非 200 的 `code` 和 `message` 表示。每个响应都在 payload 里带 `code` + `message`；HTTP 层错误的 `code` 为 HTTP 状态码。请求方向（VOICE_INPUT、AGENT_INPUT、RECORD_*、STATE_QUERY、HEALTH_QUERY）与 Agent↔MCP 工具消息（CREATE_TASK、UPLOAD_TASK、EXECUTE_TASK、TASK_RESULT、ERROR）各自保留独立类型。MCP 外层 JSON-RPC、初始化、工具发现以及 SDK 参数校验/协议错误仍使用标准 MCP 协议；LLM 的 OpenAI 兼容调用也遵循模型提供方协议，不改第三方协议。

LLM 只提出业务参数，不生成 header。MCPSession 在发送工具调用前补充消息编号和 Agent → MCP 路由；接收时验证信封、来源/目标和关联编号，再把 payload 交给 Assistant 的业务模型校验。内部 tool_call 事件和历史工具结果用于编排、状态维护与模型上下文，不再通过地面站的操作响应暴露。

## 3. 地面站 → Agent HTTP 接口

/api/voice 与 /api/text 是同一套业务处理的两种输入入口，每轮二选一；/api/text 为可选文字入口，仅接入语音时无需接入它。语音先经 ASR，文字直接进入相同的语义提取和任务操作；澄清补参也可继续用语音，最终 AGENT_OUTPUT 结构一致。

请求均使用 Content-Type: application/json，所有路径使用 POST；语音成功响应使用 application/x-ndjson，其他响应使用 application/json。表中入参由 React 发给 Agent，出参由 Agent 返回 React；入参和出参是信封的 payload。所有响应的 `header.msg_type` 均为 `AGENT_OUTPUT`，payload 都带 `code` + `message`；成功响应由 `payload.type` 区分，错误响应以非 200 的 `code` 表示且不带 `type`。

| 路径 | 请求 msg_type | 入参 payload | 响应 msg_type | 出参 payload.type | 出参 payload |
|---|---|---|---|---|---|
| /api/voice | VOICE_INPUT | {audio_format: "wav", audio_base64: "…"} | AGENT_OUTPUT | asr → task_result/clarify | 先转写 text，后本次结果；错误由 code 表示 |
| /api/text | AGENT_INPUT | {text} | AGENT_OUTPUT | task_result/clarify | 本次澄清或成功结果；错误由 code 表示 |
| /api/record | RECORD_COMMAND | {type: record_start} | AGENT_OUTPUT | record_start | 仅 type、code、message |
| /api/record/status | RECORD_STATUS | {} | AGENT_OUTPUT | record_status | {listening, level, seconds, max_seconds} |
| /api/record | RECORD_COMMAND | {type: record_stop} | AGENT_OUTPUT | asr → task_result/clarify | 先转写 text，后本次结果；错误由 code 表示 |
| /api/state | STATE_QUERY | {} | AGENT_OUTPUT | state | {session_id, revision, tasks, last_task, pending, changes} |
| /health | HEALTH_QUERY | {} | AGENT_OUTPUT | health | {status: "ok", service: "agent-web", asr_ready} |

header.src 为 FRONT / 地面站编号，header.dst 固定 BACKGROUND / AGENT-01。Agent 响应 src 为自己，dst 为原 src；请求与响应的对应关系由 HTTP 请求/响应本身确定，信封不再放关联编号。/api/record 使用同一个 POST 路径，通过 payload.type 的 record_start / record_stop 选择操作；record_start 返回 code=200 表示监听已开启，录音时长上限和实时监听状态由 /api/record/status 查询；表中 /health 为可选诊断接口，自带地面站不再调用它；/api/state 也只在页面加载与每次操作完成后查询，不做周期轮询。

语音 payload 使用完整 WAV 的标准 Base64，不带 Data URL 前缀或空白。解码后必须是 16 kHz、单声道、PCM16 WAV，最大 8 MiB；含信封的 JSON 上限为 11,250,348 字节。其他请求 JSON 上限为 64 KiB。/api/voice 成功响应采用 application/x-ndjson：ASR 完成立即发送 `AGENT_OUTPUT`，`payload.type` 为 `asr`、`payload.text` 为转写文本，并刷新连接；Agent 同时继续内部语义提取，处理完成再发送第二条 `AGENT_OUTPUT` 并结束响应。每条消息仍为 header + payload JSON，在传输时压缩为一行并以换行分隔；两条响应均对应同一次最初语音请求，对应关系由该响应本身确定，msg_id 各自唯一。前端逐行读取，先展示转写再展示结果，不回传识别文本；/api/text 仅用于手动文字输入，继续返回普通 application/json。

/api/record 和 /api/record/status 是 /api/voice 的服务端录音入口：麦克风由 Agent 的 inputs/recorder.py 采集（16 kHz 单声道 float32），/api/record 的 record_start 操作打开设备并返回 `payload.type=record_start` 的确认消息（`code=200` 表示成功），record_stop 操作复用 /api/voice 的转写与后续处理，同样以 application/x-ndjson 先回 `payload.type=asr` 再回本次结果；/api/record/status 返回 `payload.type=record_status` 的实时快照 `{listening, level, seconds, max_seconds}`。录音按 `record:<src>:<msg_id>` 前缀去重，重放只返回缓存。达到 max_seconds（默认 90）时服务端自动停止监听。

响应 payload 只返回一个本次结果（都带 code + message）：`{type: "task_result", tool, task_id, status, task}` 或 `{type: "clarify", text}`。语音转写通过独立的 `payload.type=asr` 帧先行返回，最终结果不重复携带转写。业务错误和 HTTP 层错误都使用非 200 的 `code` 与 `message`，不设置 `payload.type`。不返回 events、工具调用参数、完整 state、changes 或本机 file；状态和变化只通过 /api/state 查询。语音流开始后的服务异常/超时通过流内 `AGENT_OUTPUT` 消息返回错误码，客户端也要检查是否已收到终止结果。原裸 JSON、X-Msg-Id、原始 WAV 请求和 GET 查询已停止使用，GET 返回 405；不会同时兼容两套格式。

## 3.1 A1：语音输入（文件上传）

地面站 → Agent：`POST /api/voice`。语音输入形式：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000001",
    "msg_type": "VOICE_INPUT",
    "version": "1.0.0",
    "src": { "type": "FRONT", "id": "GS-01" },
    "dst": { "type": "BACKGROUND", "id": "AGENT-01" }
  },
  "payload": {
    "audio_format": "wav",
    "audio_base64": "<完整WAV文件的Base64字符串>"
  }
}
```

| payload 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| audio_format | string | 是 | 固定 wav |
| audio_base64 | string | 是 | 完整 WAV 文件的标准 Base64，包含 WAV 文件头；不带 Data URL 前缀、空白或换行 |

解码后的音频为 16000 Hz、单声道、无压缩 PCM16 WAV，最大 8 MiB。语音 JSON 请求体最大 11,250,348 字节。A1 供自行录音并编码 WAV 的外部地面站使用；自带前端已改用 A5–A7 的服务端录音，单次上限由 A5 返回的 max_seconds 控制（默认 90 秒）。

Agent 返回 HTTP 200，`Content-Type: application/x-ndjson; charset=utf-8`，同一次 HTTP 响应按顺序分两阶段发送。浏览器应持续读取响应体，按换行符解析完整 JSON，不能等待完整响应后再调用 response.json()。两帧的 `header.msg_type` 都是 `AGENT_OUTPUT`。

**第一条：转写帧（`payload.type: "asr"`）。** ASR 识别完成立即发送并刷新连接；地面站立即把 `payload.text` 显示为用户消息，进入“Agent 正在处理”。此时语义提取和工具操作尚未完成。

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000002",
    "msg_type": "AGENT_OUTPUT",
    "version": "1.0.0",
    "src": { "type": "BACKGROUND", "id": "AGENT-01" },
    "dst": { "type": "FRONT", "id": "GS-01" }
  },
  "payload": {
    "type": "asr",
    "code": 200,
    "message": "识别成功",
    "text": "新增名为晨曦的放飞前出任务，原地起飞，起飞高度50米"
  }
}
```

**第二条：本次结果。** Agent 内部直接把识别文本交给 LLM，按需调用工具；完成后发送本次结果并关闭响应。不重复返回识别文本。成功或需要补充参数时，`payload.type` 为 `task_result` 或 `clarify`；错误由非 200 的 `code` 和 `message` 表示。

识别成功但需要补参时，第二条为 `payload.type: "clarify"`（code 200）。ASR 空结果或失败时不调用 LLM，直接返回 HTTP 422/500 的 `AGENT_OUTPUT` JSON（`code` 为 HTTP 状态码、`message` 为原因）；已发送转写帧后的服务超时或异常以 HTTP 200 流内的 `AGENT_OUTPUT` 消息结束（`code` 取 5xx、`message` 为原因）。

## 3.2 A2：文字输入（可选）

用于支持文字输入的地面站提交键盘口令，也可用文字补充参数；它与 A1 是可替代的输入入口，不是语音流程的下一步。地面站 → Agent：`POST /api/text`：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000003",
    "msg_type": "AGENT_INPUT",
    "version": "1.0.0",
    "src": { "type": "FRONT", "id": "GS-01" },
    "dst": { "type": "BACKGROUND", "id": "AGENT-01" }
  },
  "payload": {
    "text": "新增名为晨曦的放飞前出任务，原地起飞，起飞高度50米"
  }
}
```

payload.text 为非空 string，服务端去除首尾空白；整个 JSON 请求体最大 64 KiB。text 是本轮口令，不是需要界面维护或回传的上下文。

Agent → 地面站：HTTP 200，`header.msg_type` 为 `AGENT_OUTPUT`；成功/澄清结果的 `payload.type` 为 `task_result` / `clarify`，错误由 `payload.code` 表示。

## 3.3 通用处理结果（A1、A2、A7 共用）

以下字段和任务阶段同时适用于语音和文字输入，不依赖是否接入 A2。

| payload.type / 错误 | code | message | 字段 | 含义 |
|---|---|---|---|---|
| task_result | 200 | 操作成功 | tool、task_id、status、task | 一份操作后的完整任务参数 |
| clarify | 200 | 需要补充参数 | text | 澄清问题或普通文字回复（模型完整答复），无工具结果 |
| 错误（无 type） | 非 200 错误码 | 错误说明 | code、message | 业务或 HTTP 错误 |

A1/A7 的转写通过前一条 `payload.type=asr` 帧单独返回，本次结果不重复携带转写。三个阶段的成功结果使用相同字段：

| tool | status | task |
|---|---|---|
| create_task | draft | 创建后的完整任务 |
| upload_task | uploaded | 上传后的完整任务 |
| execute_task | executing | 执行后的完整任务，参数保留 |

澄清时 payload 为 `{"type":"clarify","code":200,"message":"需要补充参数","text":"请补充起飞高度（单位：米）。"}`；业务失败时如 `{"code":500,"message":"请先上传任务。"}`。clarify.text 是模型的完整答复，可能长于状态快照里的 pending——后者是它截取前 200 字的精简目标，用于状态栏和下一轮提示词；两者不一定相等，界面应把 clarify.text 原样展示。

### 三阶段交互

| 阶段 | 用户口令示例 | 返回状态 |
|---|---|---|
| 创建 | 新增名为晨曦的放飞前出任务，原地起飞，起飞高度50米 | draft |
| 保存并模拟上传 | 上传晨曦任务 | uploaded |
| 模拟执行 | 执行晨曦任务 | executing |

每轮口令按输入方式选择 A1 或可选的 A2；创建、上传、执行以及澄清补参均可全程使用 A1。创建不自动上传或执行。上传在 Agent 侧保存文件并更新状态，对外不返回本机 file 路径；执行只更新模拟状态，不连接真实飞控。

## 3.4 A3：查询任务状态和参数

地面站 → Agent：`POST /api/state`，请求 payload 为 `{}`：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-00000000000b",
    "msg_type": "STATE_QUERY",
    "version": "1.0.0",
    "src": { "type": "FRONT", "id": "GS-01" },
    "dst": { "type": "BACKGROUND", "id": "AGENT-01" }
  },
  "payload": {}
}
```

Agent → 地面站：HTTP 200，`payload.type` 为 `state`。以下为 Agent 刚启动、尚无任务时的完整状态响应：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-00000000000c",
    "msg_type": "AGENT_OUTPUT",
    "version": "1.0.0",
    "src": { "type": "BACKGROUND", "id": "AGENT-01" },
    "dst": { "type": "FRONT", "id": "GS-01" }
  },
  "payload": {
    "type": "state",
    "code": 200,
    "message": "状态查询成功",
    "session_id": "0123456789abcdef0123456789abcdef",
    "revision": 0,
    "tasks": [],
    "last_task": null,
    "pending": null,
    "changes": []
  }
}
```

| payload 字段 | 类型 | 说明 |
|---|---|---|
| session\_id | string | Agent 本次运行标识；发生变化时切换会话 |
| revision | integer | 同一会话单调递增；忽略低于当前版本的快照，不假设每次只加 1 |
| tasks | array | 完整列表，按 task\_id 展示 status 和完整 task 参数 |
| last\_task | string / null | 最近成功任务的可读描述，不从中解析结构化字段 |
| pending | string / null | 待补充的澄清目标，最多 200 字；是本轮结果中 clarify.text 的前 200 字精简版，两者不一定相等 |
| changes | array | 最近最多 100 条变化；before/after 为独立任务快照，创建时 before 为 null |

changes[].at 为 ISO 8601 UTC 时间。tasks 的每条数据为 {task_id, status, task}，task 结构与 A1/A2/A7 成功结果中的 task 相同。changes 保留最近 100 条 before/after 变化，只在 A3 返回。

界面在页面加载时查询一次 A3，并在每次操作（含 A1/A2/A7）完成后主动查询一次，不做周期轮询；A1/A2/A7 本身不返回状态快照。上传和执行后保留完整任务参数。状态按 draft → uploaded → executing 流转；completed、aborted 仅预留，当前没有完成、终止或参数修改接口。会话不持久化，重启 Agent 后任务和变化清空；已保存文件不自动恢复会话。所有页面共享同一个 Agent 会话。

## 3.5 A4：查询健康状态（可选诊断）

地面站 → Agent：`POST /health`，请求 payload 为 `{}`。Agent 返回 HTTP 200，`payload.type` 为 `health`：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000008",
    "msg_type": "AGENT_OUTPUT",
    "version": "1.0.0",
    "src": { "type": "BACKGROUND", "id": "AGENT-01" },
    "dst": { "type": "FRONT", "id": "GS-01" }
  },
  "payload": {
    "type": "health",
    "code": 200,
    "message": "服务正常",
    "status": "ok",
    "service": "agent-web",
    "asr_ready": true
  }
}
```

asr\_ready 只表示 ASR 模型已加载，不保证 LLM 或任务操作均可用。A4 为可选诊断接口，自带地面站不再调用它；录音是否成功开启由 /api/record 的 record_start 响应 `code=200` 判断。

## 4. 阶段一：创建草稿

### 4.1 Agent → MCP：create_task 入参

发送方：Agent MCP 客户端；接收方：MCP create_task。以下为工具 arguments 的完整内容，不含标准 MCP JSON-RPC 外层。payload 模型是 CreateTaskPayload。

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000010",
    "msg_type": "CREATE_TASK",
    "version": "1.0.0",
    "src": {
      "type": "BACKGROUND",
      "id": "AGENT-01"
    },
    "dst": {
      "type": "BACKGROUND",
      "id": "MCP-01"
    }
  },
  "payload": {
    "action": "create_task",
    "task": {
      "task_type": "放飞前出任务",
      "task_name": "晨曦",
      "parameters": {
        "mode": "原地起飞",
        "takeoff_altitude": 50.0
      }
    }
  }
}
```

缺少模式、高度或编队参数时，Agent 先向界面澄清，不调用工具。CreateTaskArguments 是 LLM 提案校验模型，只含 payload；完整传输结构是 Message[CreateTaskPayload]。

### 4.2 MCP → Agent：create_task 成功出参

返回方：MCP；接收方：Agent；payload 模型 DraftTaskResult。

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000011",
    "msg_type": "TASK_RESULT",
    "version": "1.0.0",
    "src": {
      "type": "BACKGROUND",
      "id": "MCP-01"
    },
    "dst": {
      "type": "BACKGROUND",
      "id": "AGENT-01"
    }
  },
  "payload": {
    "status": "draft",
    "task_id": "TASK-0123456789abcdef0123456789abcdef",
    "task": {
      "task_type": "放飞前出任务",
      "task_name": "晨曦",
      "parameters": {
        "mode": "原地起飞",
        "takeoff_altitude": 50.0
      }
    }
  }
}
```

MCP 在创建时立即生成 task_id，补全缺省名称并保存到 TaskStore，状态 draft。不保存上传文件、不上传、不执行。编号经 MCP → Agent → React 返回，不由地面站生成或回传。

### 4.3 Agent → React：创建展示

原语音或文本请求返回 AGENT_OUTPUT，payload 为 {type: "task_result", code: 0, message: "操作成功", tool: "create_task", task_id, status: "draft", task}。只携带本次任务的一份完整参数。Agent 内部记录创建变化，界面另查 /api/state 同步列表；不回传 MCP 的传输 header 或调用参数。

## 7. 错误、状态和重试

MCP 业务失败返回 ERROR 信封，Agent 将 payload.error 转为对外 AGENT_OUTPUT 的错误响应（非 200 `code` 和错误 `message`，不带 type），失败不返回成功任务结果。示例：

```json
{
  "header": {
    "msg_id": "MSG-550e8400-e29b-41d4-a716-000000000016",
    "msg_type": "ERROR",
    "version": "1.0.0",
    "src": {
      "type": "BACKGROUND",
      "id": "MCP-01"
    },
    "dst": {
      "type": "BACKGROUND",
      "id": "AGENT-01"
    }
  },
  "payload": {
    "error": "任务当前状态为 draft，不能转到 executing，请按 创建→上传→执行 顺序操作"
  }
}
```

MCP 的参数模型校验或协议失败由 SDK 的 is_error 表达，Agent 转换为非 200 `code` 和错误 `message` 的 AGENT_OUTPUT。HTTP 参数、消息头、路由、长度错误为 400，媒体类型错误 415，音频或空转写 422，ASR/I/O 错误 500，超时 504；这些 HTTP 响应也都使用 `AGENT_OUTPUT` 信封，`payload` 只有 `code`（HTTP 状态码）+ `message`（错误说明）。详细错误契约见地面站对接文档。

状态严格按 draft → uploaded → executing。completed、aborted 只预留，没有对应工具。未知编号、重复上传、跳步执行、重复执行均拒绝。

Agent 快照含单调递增 revision、完整任务、last_task、pending 和最近 100 条 changes；变化记录含 before/after、UTC 时间和触发请求的 MSG-UUID。重启清空会话，文件不自动恢复。同一会话任务目录跨对话窗口保留，多个页面共享状态。

A1/A2 按端点 + src.id + msg_id 缓存最近共 256 个响应。重试保留完整信封，新口令/录音用新 UUID。Agent 超时 180 秒、界面等待 190 秒；超时不取消已开始操作，先查状态再用原信封重试。重启或缓存淘汰后不保证旧请求去重。

## 8. 参数和运行配置

任务类型当前为 放飞前出任务。原地起飞必填 takeoff_altitude（>0 m）；在指定位置展开还需 formation：C型必填 open_angle（0<角度≤360度）、radius（>0 m）、position；U型必填 formation_length、formation_width（均>0 m）、position。position 是 WGS84 {longitude, latitude}，范围经度 [-180,180]、纬度 [-90,90]，拒绝无穷和 NaN。名称长度 1–64，默认“任务类型-编号前8位hex”，名称不作唯一键，重名选择需澄清。

```sh
# Agent 加载 ASR、模型客户端，并自动启动 MCP
python main.py web --task-output-dir /绝对路径/任务目录

# React 地面站：另一终端
cd web
npm run dev
```

输出目录默认 output/，通过 TASK_OUTPUT_DIR 传给 MCP 子进程。文本 CLI 也支持 --task-output-dir；mcp 子命令仅用于单独启动 stdio 服务。

ASR 默认 SeACo-Paraformer，加载 config/asr_hotwords.txt 的 22 个领域词，并向后续录音加入已创建任务名称；可通过 --asr-hotwords-file 修改词表。首次命名仍依赖模型识别，热词不保证消除同音字错误。

扩展需更新 shared/contracts.py 的 TASK_TYPES / LAUNCH_MODES / FORMATION_TYPES、MSG_TYPES、提示词和测试；新增工具还需登记 assistant/tools.py 的参数/结果校验和 MCP 的业务信封映射。根目录 接口.json 是历史协议示例，当前运行不读取它。
