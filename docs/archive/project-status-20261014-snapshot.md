# 语音地面站助手：当前状态与后续工作

更新时间：2026-10-14（Asia/Shanghai）  
运行状态检查：2026-10-14 11:18  
依据：当前源代码、现有文档、本次回归测试，以及 2026-10-14 的模型与缓存实测记录。

## 1. 当前定位

项目已完成一个可扩展的本地语音地面站助手原型：输入文本或录音，由模型提出新增任务调用，经严格校验后，通过真实 MCP 和 HTTP 发送到独立模拟地面站，保存任务并返回结果。

当前执行范围是**创建模拟任务记录**。尚未连接真实地面站业务程序或飞控，也未实现飞行控制。模型提出调用建议；任务是否创建成功，以执行层实际返回并通过校验的结果为准。

```mermaid
flowchart LR
    A[文本 / 录音 / 麦克风] --> B[输入层：音频先经 ASR]
    B --> C[L1：Ornith 提出调用]
    C --> D[L2：工具与参数校验]
    D --> E[L3：MCP → HTTP]
    E --> F[L4：模拟地面站校验并保存]
    F --> G[验证返回结果并反馈用户]
```

### 当前支持的任务

MCP **只有一个工具**：`create_task`。以下五种任务变体属于该工具的参数分支，不是五个不同工具。

| 任务类型 | 模式 / 参数 | 要求 |
|---|---|---|
| 放飞前出任务 | 原地起飞 | 不带位置或区域 |
| 放飞前出任务 | 在指定位置展开 | WGS84 经度、纬度 |
| 放飞前出任务 | 在指定区域展开 | 按边界顺序提供至少三个不同顶点 |
| 编队飞行任务 | C 型 | `formation_type=C型` |
| 编队飞行任务 | U 型 | `formation_type=U型` |

坐标范围和重复顶点已校验；完整多边形几何、地图位置解析与任务可行性尚未实现。模型不得编造缺失的坐标。

## 3. 每轮提示词与会话的实际行为

每条口令独立调用模型，发送：

```text
固定 SYSTEM_PROMPT + 当前会话发现并注册的工具完整 Schema + 本条用户文本
```

提示词位于 [prompts.py](../../inference/prompts.py)，请求构造位于 [models.py](../../inference/models.py)。当前每轮都发送固定提示词和同一组工具定义。前缀缓存复用重复部分的计算结果，并不省略请求中的提示词。

麦克风会话复用了 ASR 模型和 MCP 连接，但**没有保存历史对话或待补全任务**。因此：

> 用户：新增编队任务。  
> 助手：需要 C 型还是 U 型？  
> 用户：U 型。

目前第三句不会自动补齐第一句的任务。模型可以提出澄清，但程序没有续接澄清的状态机制。每条口令仍是独立提案流程。

## 4. 验证结果与边界

### 自动化测试

本次重新运行：

```sh
python -m unittest discover -s tests -v
```

结果：**25 项测试全部通过**，用时约 7.93 秒。

覆盖内容包括：五种任务、非法参数拒绝、不写文件、真实 MCP/HTTP 调用、消息模板不被改写、返回结果一致性、ASR 文件/连续麦克风输入接入、模型复用、取消时资源关闭、替换模型与工具接入、新增工具注册、CLI 入口。

这些测试中的 ASR 转写采用注入结果，本地模型 HTTP 测试也使用模拟响应。它们验证程序流程与边界，不等于真实语音和真实模型的全面准确率验证。

### 已有真实模型与 ASR 验证

- 迁移后的 Paraformer 对模型自带音频转写为“欢迎大家来体验达摩院推出的语音识别模型”。
- 缓存测试中，真实 Ornith 对五种完整任务口令的调用参数核对通过。
- 真实 oMLX → L2 → MCP → HTTP → 临时模拟地面站链路通过，成功保存 U 型编队任务。
- 一条“不要新增 C 型编队任务”的真实模型输入没有工具调用。

上述结果是有限样例验证。自由表述、模糊时间/地点、复杂否定、噪声口令和真实麦克风整体准确率仍需建立评测集。

### 性能记录

历史测试环境：M1 Max（24 核 GPU、64 GB 内存），oMLX 0.6.3rc2，Ornith-1.5-35B-A3B-MLX-6bit，默认思考模式。

| 同一原地起飞口令 | 缓存关闭 | 缓存命中后 |
|---|---:|---:|
| 命中 token | 0 | 1,536 |
| 首 token 等待 | 4.23 秒 | 约 0.94 秒 |
| 模型请求总耗时 | 6.74 秒 | 约 3.19 秒 |
| 输出 token | 137 | 113 |

512-token 分块后输出长度也发生变化，不能把总耗时差异全部归因于缓存。第一次加载模型与建立缓存仍有较大开销；长输出任务仍可能明显慢于简单任务。历史生成阶段速度约 46–58 tok/s，不能直接和某条非流式日志的“输出 token ÷ 整次请求耗时”混为一谈。

当前代码已有 Schema 引用展开，历史测速记录不代表此后每次 Schema 调整的最新性能；应使用当前代码重新采集 token 数、缓存命中、首 token 等待及总耗时。

完整记录见 [缓存测试报告](../cache-performance.md) 和 [原始数据](../cache-benchmark-20261014.json)。

oMLX 暂停时，助手会等待模型响应直至超时。在原启动终端中，若是通过 Ctrl+Z 暂停，可用 `fg` 恢复；Ctrl+C 用于停止服务。已有监听服务时，应先确认其状态，避免再次启动造成端口冲突。本次文档整理没有恢复或重启该暂停进程。

Metal 的 48 GB 默认限制、oMLX 的静态预算和动态保护上限属于内存预算信息；动态上限不是当前占用。当前模型约 27 GB、热缓存 2 GiB，短口令场景的现有验证未要求提高系统 GPU 内存限制。

## 6. 已讨论、尚未接入的方案

### EmbeddingGemma 2 工具召回

已讨论的设计是：先从 MCP 工具目录检索候选，再把候选工具完整 Schema 交给 Ornith 决策与填参。

```text
启动 / 工具目录更新：MCP 发现 → 已注册工具过滤 → 工具描述向量化 → 索引
每条用户口令：ASR 文本 → 查询向量 → 候选工具 → Ornith → 校验 → MCP
```

目前**未接入 EmbeddingGemma 2，未创建工具向量索引，也未完成 Mac 本机部署兼容性或速度测试**。该模型的语义检索能力可用于这个设计，见 [官方模型说明](https://huggingface.co/google/embeddinggemma-2)。

目前只有一个 `create_task` 工具，候选筛选无法减少工具数量。工具增多后再实测其价值：比较正确工具召回率、候选 token 数、嵌入耗时、缓存命中和端到端响应时间。

向量相似度只能提供候选，无法确认用户允许执行，也无法证明参数完整。否定句可能检索到相关工具；执行仍需 Ornith 判断及 L2 校验。动态工具子集会改变请求前缀，需要稳定工具顺序，并测量实际缓存收益。

## 8. 下一阶段建议验收场景

| 场景 | 预期行为 |
|---|---|
| 完整原地起飞口令 | 创建一次任务，返回可关联的实际任务编号 |
| “新增编队任务”后回答“U 型” | 续接待补全任务；参数完整后仅创建一次 |
| 指定位置但没有坐标 | 请求补充；补齐前不创建 |
| 澄清期间说“取消，改成 C 型编队” | 结束旧待办，按新意图重新处理，避免旧参数混入 |
| “不要新增任务” | 无创建调用；明确取消现有待补全流程的规则 |
| HTTP 回复超时后重复口令 | 查询或识别原请求结果，避免重复任务 |
| 多工具候选检索错误或没有相关工具 | 不执行错误工具；按定义的扩大候选或澄清策略处理 |
| 模型、ASR 或 MCP 出错 | 显示可定位的失败原因；资源正确关闭；后续输入按会话策略处理 |

多轮、幂等和工具召回相关场景目前属于后续验收目标。现有实现仅对其中已具备的单条任务流程提供验证。
